01 Sync & Async

Today, we will improve a small web page in three steps. First, we will make the page respond while it waits. Next, we will reduce the total waiting time for three independent requests. Finally, we will stop an old search response from replacing the current result.

You will work with a project that already runs. The interface and server are provided, and we will edit just one JavaScript file. For each change, we will run the current version, change a function, and look at the result in the browser.

Keep your editor and browser ready. Let’s begin with the workshop steps.

Here is our route through the workshop. We will first download and run the starter. Then we will work through the three tabs on the page.

07 Find the blocking call

In practice.js, find wait. It currently calls busyWork and then returns Promise.resolve.

The first line is the problem. busyWork repeatedly checks the clock until the requested time has passed. While it does that, it keeps the page’s main thread busy. Other work on that thread has to wait.

The Promise is returned only after the blocking work has finished. Returning a Promise at that point cannot give back the time during which the page was frozen.

We will keep busyWork as our comparison. On the next slide, replace only the wait function so that it registers a timer instead of repeatedly checking the clock.

08 Replace wait with a timer

Replace the entire wait function with this version. Keep the same function name and the ms parameter.

The function now returns a new Promise. Inside it, setTimeout schedules a callback using the delay we received. When the timer callback runs, it calls resolve, which completes this Promise.

The page’s button handler is already waiting for this Promise. While the timer is pending, our function is no longer occupying the main thread with a loop. That gives the page an opportunity to handle other work.

Please save the file and reload the browser. Make sure you replaced the old function rather than adding a second function with the same name.

13 Read the provided sequence

Find loadSequential in practice.js. The supplied task function knows how to send a request and update its bar and log. Zero means profile, one means posts, and two means notifications.

Here, we call task zero and await its result. Only then do we call task one. The same pattern repeats for task two. That is why the bars start one after another.

Keep this function unchanged so we can compare the two schedules. Now find loadConcurrent. In the starter, it contains the same sequential code. On the next slide, we will replace that function and leave this one as our baseline.

14 Start all three before waiting

Replace loadConcurrent with this shorter version. The first line calls all three tasks and keeps their Promises in an array named jobs. Because there is no await between those calls, all three requests can start before we wait for their results.

The second line returns Promise.all for that array. The supplied button handler waits for this combined Promise. Its successful results follow the input order, even if the requests finish in a different order.

These requests are independent, so overlapping their waits is appropriate here. Save the file and reload the browser. Then we will run both versions again to compare them.

We did not make each individual request faster. We changed their start times so that their waiting periods overlap. Compare the two totals on your own screen. Next, we will see whether the browser’s Network panel shows the same pattern.

17 Follow one request through the helper

Open lab.js and find the fetch call inside the request function. We are reading this helper; you do not need to edit it.

The parameters include kind, delay, and query. URLSearchParams turns them into the query string you just saw in Network. fetch sends the request, and await waits for the Response. The helper then checks response.ok and reads the JSON body.

A received HTTP error needs that explicit status check. Reading the body is also an asynchronous step. For now, match one request’s kind and delay to the values in Network. Then return to the browser for our final code change.

18 Reproduce the outdated search result

Open the third tab, Out-of-order responses. Click Play: java to javascript. The replay sends a search for java, then changes the input and sends a search for javascript.

Wait until both responses have arrived. The input now says javascript, but both panels in your current version should eventually show results labelled java. That result belongs to the older query.

The first two changes did not fix this problem because shouldRender still returns true for every response. Look at the response log. We will use its order to understand why the old result replaces the new one before we change that decision.

19 Match the log to the wrong result

The java request starts first, but its configured delay is sixteen hundred milliseconds. The javascript request starts one hundred and fifty milliseconds later and needs only three hundred milliseconds.

So the newer result arrives around four hundred and fifty milliseconds after the replay begins. The older result arrives later, around sixteen hundred milliseconds. If we display every response when it arrives, that older response wins at the end.

Both requests can succeed. The mistake is allowing a result for an old query to replace the current search. We will now find the condition that decides whether the right panel may update.

20 Find the decision before rendering

In lab.js, find the call to practice.shouldRender. The selected lines on this slide show where the request ID comes from and where the decision is used.

Each new search increments latest and saves that number as its own id. While that search waits, a newer search may increment latest again. The older call still keeps its original id.

After the response arrives, the code asks shouldRender whether the right panel may update. Comparing the two numbers at this point tells us whether the response is still current. Leave lab.js unchanged. We will edit the small decision function in practice.js.

21 Accept only the current ID

Return to practice.js and find shouldRender. Replace return true with return id equals equals equals latest, as shown here.

When the two numbers match, the function returns true and the right panel can display the result. When they differ, a newer search has started, so it returns false and the old result is ignored.

This does not cancel the old request. It changes whether that response may update the interface. The left panel remains unguarded so that we can compare the two behaviors.

Save the file and reload the browser. We will replay the same searches with this new condition.
